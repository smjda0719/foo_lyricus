## D-001 技术路线：原生 C++ 面板

- **决定**：走官方 SDK 的 C++ 路线，实现 DUI element + CUI panel。
- **理由**：桌面歌词、多屏置顶、Direct2D 自绘、点击穿透这些差异化能力只有在原生层才做得舒服；WebView2 路线的窗口行为受宿主（`foo_ui_webview2`）约束，且该组件为 GPL-3.0。
- **否决的备选**：WebView2 混合方案、JS 面板脚本（JScript Panel 3 / JSplitter / SMP）。

## D-002 工具集与 SDK 版本：`v145` + Windows SDK `10.0.26100`

- **决定**：不补装 v143 工具集和 10.0.19041 SDK，直接用本机现有的 **VS Professional 2026（18.8.12021.73，`v145` / MSVC 14.51.36231）+ Windows SDK 10.0.26100.0**。
- **理由**：本机只有这一套；省下 2~3 GB 下载。

### 实测核实（2026-09，SDK 已下载解压到 `3rdparty/`）

官方 SDK `2026-09-17` 的 **7 个 `.vcxproj` 全部**写着：

```
PlatformToolset             = v143
WindowsTargetPlatformVersion = 10.0
LanguageStandard            = stdcpp20
```

- `WindowsTargetPlatformVersion=10.0` 表示"用已安装的最新 10.x SDK" → 本机自动解析到 `10.0.26100.0`，**无需改动**；
- **`v143` 本机没有**（只有 `v145` / MSVC 14.51.36231），**必须改**。

### ⚠️ 修正此前的错误判断

之前根据官网那句 "Included project files are for Visual Studio 2022/2026" 推测"官方工程面向 VS2026、可直接用"——**不成立**。
官网那句话的意思是"工程能在 VS2022/2026 里打开"，**前提是装了 v143 工具集组件**。既然决定不装，就要把 toolset 重定向到 `v145`。

**影响**：官方 SDK 自带工程、以及网上 clone 的现成工程（`foo_openlyrics`、`foo_artwork`）**都要重定向**。
后者还把 `WindowsTargetPlatformVersion` 写死成 `10.0.19041.0`，这个也得改成 `10.0`（跟随最新）或 `10.0.26100.0`。

## D-005 窗口模糊：用 DWM 系统背景，不引入 Windows App SDK

- **决定**：独立操作面板的 Mica/Acrylic 走 **DWM 系统背景**（`DwmSetWindowAttribute` + `DWMWA_SYSTEMBACKDROP_TYPE`）。
- **理由**：微软官方 "Apply Mica in Win32" 文档要求 Windows App SDK（`MicaController` + `Compositor` + C++/WinRT + `DispatcherQueue` + 用户侧 Windows App Runtime 可再发行包）。对一个注入 foobar2000 进程的组件来说，初始化 WinRT apartment 和引入运行时依赖**代价过大、风险高**。
- **实测确认**：`DWM_SYSTEMBACKDROP_TYPE`（`dwmapi.h`）**最低支持 Windows 11 Build 22621**，本机 22631 ✓。
  取值：`DWMSBT_MAINWINDOW`=2（Mica）、`DWMSBT_TRANSIENTWINDOW`=3（**Desktop Acrylic**，毛玻璃）、`DWMSBT_TABBEDWINDOW`=4（Mica Alt）。效果绘制在**整个窗口边界之下**，正合独立面板所需。
- **额外优势**：Windows SDK 26100 的 `dwmapi.h` 已定义这些常量（含 `DWMWA_USE_IMMERSIVE_DARK_MODE`=20），**无需魔数**。
- **降级**：Win10 及更早走 `SetWindowCompositionAttribute` + `ACCENT_ENABLE_ACRYLICBLURBEHIND`（未公开 API；SDK 的 `libPPUI/DarkMode.cpp` 已有同族调用先例）。
- **已知问题**：Win11 上 Acrylic 窗口**拖动时可能卡顿**（微软已承认），缓解办法是拖动期间临时切不透明。

## D-006 构建环境：MSBuild 用 Professional 那一套

- **决定**：用 `D:\VS studio\MSBuild\Current\Bin\MSBuild.exe`（VS2026 Professional）。
- **理由**：**ATL 只装在 Professional 下**（`D:\VS studio\VC\Tools\MSVC\14.51.36231\atlmfc` 存在），BuildTools 那套（`C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Tools\MSVC\14.51.36231`）**没有 atlmfc**。libPPUI 和 sdk_helpers 都需要 ATL。
- **另需自备 WTL**：SDK 不自带 `atlapp.h`，`libPPUI` 与 `foobar2000_sdk_helpers` 编译会失败（实测 `error C1083`）。

## D-007 手动安装路径：64 位宿主用 `user-components-x64`

- **决定**：手动安装组件时，目标路径是
  `%APPDATA%\foobar2000-v2\user-components-x64\<组件名>\<dll>`
  **不是** `user-components\<组件名>\<dll>`。
- **实测依据（铁证）**：foobar2000 2.25.9 (x64) 于 2026-09-22 23:17:18 启动时**自己创建了** `user-components-x64` 与 `user-components-x64\pending` 两个目录；而 `user-components` 目录**此前根本不存在**（是我们手工建的）。
- **静态证据**：`foobar2000.exe` 内含字符串 `user-components` 与 **`user-components-`（带连字符，说明是前缀）**，以及 `Could not list pending components directory`。即目录名 = `user-components` + 架构后缀。
- **推论**：32 位宿主用 `user-components`，64 位宿主用 `user-components-x64`（同一个 profile 可被两种架构共用而不打架）。
- ⚠️ **打包结构不受影响**：`.fb2k-component` 内部仍是「根目录 x86 DLL + `x64/` 子目录 x64 DLL」，由播放器安装器自行挑选架构，见 D-004。

## D-008 网络：GitHub 走本地 8902 代理

- **决定**：从 GitHub 下载（源码包、Release 资产等）时使用代理 `http://127.0.0.1:8902`。
- **格式**：`curl.exe -x http://127.0.0.1:8902 -L -o <输出> <url>`
- **实例验证**：直连下载 WTL 得到 2,023,776 字节的**截断包**（7-Zip 报 `Unexpected end of archive`）；走代理得到 **5,810,309 字节**的完整包，`7z t` 校验 `Everything is Ok`。
- **注意**：`web_fetch` / `web_search` 工具走的是另一条链路，**无法指定该代理**；只有本机 curl / PowerShell 发起的请求能用。

## D-009 绝不对客户区使用 `DwmExtendFrameIntoClientArea(-1)`

- **症状**：面板一片空白（只有背景，没有文字）。**按一下 `PrintScreen` 文字会闪现，取消后立刻消失**；任何截屏工具都能"看到"内容，肉眼看不到。
- **原因**：把整个客户区变成 DWM "边框"之后，客户区里的 GDI 绘制内容**不会被 DWM 呈现到屏幕上**。截屏动作会强制重新合成，所以只有截屏时能看到。
- **教训**：**"截图能看见、肉眼看不见"是这个 bug 的特征**，不是截图工具的问题。排查时如果双方观测不一致，先怀疑"呈现"而不是"绘制"。
- **结论**：DWM 系统背景材质（`DWMWA_SYSTEMBACKDROP_TYPE`）与普通 GDI 绘制**不兼容**。该 API 调用全部返回 `S_OK`，但"接受设置"不等于"正确显示"——不要以 HRESULT 判断成败。

## D-010 面板渲染改用分层窗口（`UpdateLayeredWindow`）

- **决定**：面板默认走**分层窗口 + 逐像素 alpha** 渲染：自建 32bpp DIB（`BITMAPV5HEADER` + `BI_BITFIELDS`），手工按 BGRA 写入底色与 alpha，再用 GDI 画文字（**GDI 只改 RGB，不碰 alpha**），最后 `UpdateLayeredWindow` 提交。
- **理由**：
  1. 不依赖 DWM 材质，绕开 D-009 的坑；
  2. 解决"文字背后出现黑色方块"——不自己铺底时，GDI 往透明表面写字会把文字范围写成不透明黑底；
  3. 真透明可控（当前整体 alpha 215/255），后续要做"背景半透明 + 文字全不透明"只需分别写 alpha。
- **代价**：没有真模糊（毛玻璃）。要做真模糊需要 DirectComposition + D2D，属于后续里程碑。
- **注意**：`UpdateLayeredWindow` 与 `SetLayeredWindowAttributes` **互斥**，不能同时用；分层模式下画面不经过 `WM_PAINT`，必须在 `WM_MOVE`/`WM_SIZE`/显示时主动重提交。
- **已知待优化**：目前每次重绘都新建 DIB 并逐像素填充，`WM_MOVE` 期间会很浪费。M2 之前应改为缓存 DIB。

## D-011 分层渲染必须同时做「alpha 修正」和「预乘 alpha」

- **症状**：面板成功透明了，但**文字也跟着透明**——发灰、发糊、像蒙了一层。
- **两个独立原因，只修一个不够**：
  1. **GDI 只写 RGB，从不碰 alpha 通道** → 文字像素的 alpha 仍是底色的 215；
  2. **`UpdateLayeredWindow(ULW_ALPHA)` 要求源位图是预乘 alpha 的**（RGB 已乘 `alpha/255`），直接写非预乘值会让整张图偏暗。
- **修法**：画完文字后扫一遍像素 —— 与底色不同的即文字（含抗锯齿边缘），把 alpha 提到 255；然后整图做一次预乘。
- **代价**：抗锯齿边缘被当作实心像素处理，边缘会略硬。要更精细得改用 GDI+ 或 Direct2D 绘制文字（它们会正确写 alpha）。
- **实现位置**：`src/control_window.cpp` 的 `RenderLayered()`。

## D-012 面板不用系统标准控件，一律自绘

- **决定**：M2 的播放控制按钮、进度条、音量条**全部自绘**，不使用 `BUTTON` / `msctls_trackbar32` 等标准控件。
- **来源**：用户经验——标准控件在透明底上表现可能很差。
- **架构层面的硬约束（比"表现差"更根本）**：分层窗口通过 `UpdateLayeredWindow` 提交位图，**子窗口控件无法参与这种合成**。标准控件会各自往窗口表面绘制，与逐像素 alpha 冲突，表现为控件区域变成不透明块或黑块。**所以自绘不是更优选，而是唯一可行解。**
- **与 D-011 同源**：本质都是「GDI 绘制与 alpha 合成不匹配」的同一类问题。
- **对 M2 的具体影响**：
  1. 所有控件画进**同一张 DIB**，复用 `DrawTextContent` 那一套渲染路径；
  2. **命中测试要自己算矩形**。M1 里整个客户区返回 `HTCAPTION`（所以到处都能拖），M2 必须按控件区域区分，否则点按钮会变成拖窗口；
  3. 悬停 / 按下状态与重绘要自己实现。
- **附带好处**：外观完全可控、风格统一，也顺便给了 M1 遗留的「抗锯齿边缘略硬」一个统一处理的地方（同一张 DIB 上可以用更精细的方式生成 alpha）。

## D-013 面板信息密度：歌词 2~3 行，控制键放歌词下方

- **来源**：用户建议。
- **背景**：面板默认 460x150 逻辑像素（200% 缩放下 920x300 物理）。M1 纯歌词能显示 4 行左右；M2 要加播放控制，空间立刻不够。
- **决定**：
  1. 歌词**只保留 2~3 行**（当前行 ±1），不再用 ±2；
  2. 做成**组合面板**——歌词在上、控制按键在下（播放/暂停、上一首/下一首、进度条、音量）；
  3. 底部预留条改作控制条，歌词来源信息收缩或移入提示。
- **理由**：副屏是远距离观看，行数太多反而看不清重点；控制键是高频操作，值得占固定位置。
- **对 M2 的具体影响**：
  - `kSpan` 由 2 改为 1，并考虑做成可配置（`cfg_int`）；
  - `DrawTextContent` 要明确划分三个纵向区域：**头部 / 歌词区 / 控制条**，各占固定高度，互不侵占；
  - 控制条的**命中测试必须按区域区分** —— M1 里整个客户区都返回 `HTCAPTION`（所以到处都能拖窗口），加了按钮之后不改的话，点按钮会变成拖窗口（见 D-012）。

## D-014 手动指定的歌词「按曲目记住」，不是单一键值对

- **来源**：用户从日志里发现的 bug。
- **症状**：给 A 指定的歌词 → 播放 B → 换回 A，**忘了**。日志证据：
  `手动歌词绑定的是别的曲目，解除绑定`，之后回到 A 时只剩自动匹配。
- **原因**：早期实现只存**一对**（曲目, 路径），一旦播放别的歌就整条丢弃。
- **决定**：改成一张「曲目 URL → 歌词路径」的表，存在 `cfg_manual_lyric_map`，
  **纯文本格式**（每条一行，`URL <TAB> 路径`），上限 128 条。
  用最朴素的格式是为了出问题时能直接在配置文件里看和改。
- **特例**：URL 为空的那条表示「选文件时没在播放」，会被下一首播放的曲目**收养**。
- **「恢复自动匹配歌词」**：只清除**当前曲目**的记录（外加待定记录），不再一刀切。
- **教训**：这是我的**设计不合理**，而不是实现 bug —— 代码完全按我写的逻辑工作。
  盯着代码看不出来，得从「用户预期」的角度审。

## D-015 重绘判据用「状态代次」，不用字段比对

- **症状**：换曲后画面**停留在上一首的歌词**上。日志明确显示已换曲且「未找到可用歌词」，
  但屏幕没更新。
- **原因**：重绘判据是 `if (idx != m_currentLine)`。换曲时 `m_currentLine` 被设为 `npos`，
  而空歌词算出来也是 `npos` —— **两者相等，被判定为「没变化」，于是不重绘**。
- **决定**：引入 `PlaybackState::Revision()` 状态代次，换曲 / 加载歌词 / 清除歌词时自增；
  窗口每 tick 比对，不一致就重绘。
- **理由**：字段比对要枚举所有「应该重绘」的情形，漏一个就出这种静默 bug；
  代次只要在状态变更处自增一次，天然覆盖。
- **发现方式**：**日志说状态对了，截图说画面没跟上** —— 两者分叉才暴露出来。
  只信其中一个都会漏掉。

## D-016 SVG 图标：lunasvg + 只取 alpha、颜色后置

- **决定**：图标改用用户提供的 SVG，由 **lunasvg**（MIT，纯 CPU 光栅化）渲染。
- **关键设计**：光栅化时**只保留 alpha 通道、丢弃颜色**，真正上色放到混合阶段。
  好处是**一套单色 SVG 覆盖 普通 / 悬停 / 按下 三态**，不用准备多套文件。
  代价：**支持不了多色 SVG** —— 将来若需要，得改成保留原始 RGBA。
- **顺序约束**：图标混合**必须**在分层渲染的「alpha 修正 + 预乘」**之后**。
  那一步会把所有非背景像素的 alpha 拉到 255，先混进去的图标抗锯齿边缘会被毁成硬边。
- **实测发现**：**lunasvg 不处理根元素上的 CSS `transform`**（`style="transform: scaleX(-1)"`），
  只认 SVG 自己的 `transform` 属性。而 `prev.svg` 正是靠 CSS 镜像得到的，
  结果是**上一首和下一首渲染得一模一样**。已在加载时扫描源码里的 `scaleX(-1)` 并自行水平翻转。
  （更标准的写法是 `<g transform="translate(25,0) scale(-1,1)">`，但用户文件已能正确处理。）
- **引入第三方库踩的三个坑**（均在 `build/foo_lyricus.vcxproj` 解决）：
  1. `error C4996: sprintf` —— `/sdl` 安全检查把第三方 C 代码的老式 `sprintf` 当错误
     → 加 `_CRT_SECURE_NO_WARNINGS`
  2. `无法解析的外部符号 lunasvg::Bitmap::Bitmap` —— `lunasvg.h` 在 Windows 下默认把类
     声明为 `dllimport`（它假设自己是 DLL）；静态链接必须定义 `LUNASVG_BUILD_STATIC`。
     **编译全过、链接才炸** —— 头文件里的宏分支决定符号是「导入」还是「本地」。
- **部署**：图标源文件放 `resources/`，与 DLL 同级。`build.ps1 -Install` 与
  `tools/watch-install.ps1` 都会一并拷贝 —— 漏拷的表现是图标静默消失（代码里会跳过缺失文件）。
- **代价**：DLL 从 145 KB 涨到 555 KB。lunasvg + plutovg 中相当一部分是给 `<text>` 用的
  TrueType 支持，我们用不上但代码有引用，暂时全量编译。

## D-017 歌词行数按可用高度自适应，不按宿主写死

- **症状**：DUI 元素里只显示 3 行，上下大片空白。
- **原因**：`kSpan = 1`（当前行 ±1）是按**独立面板**定的 —— 它只有 460x150 逻辑像素，
  副屏远距离观看，3 行正合适（D-013）。但 DUI 元素嵌在主窗口里可能很高，
  同一个常量就变成了浪费。
- **决定**：**行数是可用高度的函数，不是宿主的属性**。策略改为：
  当前行居中 → 上下各分一半高度预算 → 各自"能量几行就量几行" → 整块再垂直居中。
- **好处**：一份代码自动适配两种宿主；用户拉大面板时行数也跟着涨，不需要额外配置项。

## D-018 配置项只暴露「字号 / 当前行位置 / 行数上限」

- **决定**：将来做配置界面时，**不暴露裸的"显示行数"**。
- **理由**：行数本质是可用高度的函数（见 D-017）。让它变成独立参数，就会和面板高度打架
  —— 用户填 10 行但面板只放得下 3 行，徒增困惑。真正该给用户的三个旋钮是：
  | 参数 | 作用 |
  |---|---|
  | 歌词字号 | 用户说"字太小"时真正想要的是这个；**字号一变行数自然跟着变** |
  | 当前行位置比例 | 决定上下各显示几行 —— "想多看点后面的歌词"的真正旋钮 |
  | 行数上限 | 0 = 不限。防止超宽面板一次刷 30 行的**安全阀**，不是主参数 |
- **界面机制**：用 SDK 自带的 `advconfig_*` 系列（`SDK/advconfig_impl.h`），
  条目自动出现在 `Preferences → Advanced → Tools → Lyricus`，**编辑器由宿主生成，零 UI 代码**。
  比自己写 `preferences_page` + 对话框模板省得多（后者还要引 `.rc` 资源）。

## D-019 `<CharacterSet>Unicode</CharacterSet>` 是 ABI 前提，不是风格偏好

## D-042 按文件夹指定歌词线索 —— 以及「同一个判据散在多处」这个反复咬人的坑

     ```
     查「阿良良木健 哀歌」  -> 第 1 条就是它
     ```

    第三趟，**只能加机会，不能挤掉机会**。

## D-041 搜索词必须剥音轨号；以及「7 Years」那类会被误剥，所以要留后路

- **起因**：读日志发现 `02 遗忘山丘` 明明是网易云上有的（早先探过：242.8s vs 本地 242.1s，
  差 0.7 秒），日志里却是 `过曲名闸 0 条`。
- **对比实验**（同一个接口、同一个时刻）：
  ```
  查「02 遗忘山丘」 -> 青山不改与君携 85.3s / 讨好 33.1s / 遗憾 278.3s …（正确答案连前 6 都进不去）
  查「遗忘山丘」    -> 遗忘山丘 by 阿良良木健（242.8s，专辑「奇爱人生 LOVE ELEGIA」）← 完美
  ```
  **`02` 这个前缀把搜索整个带偏了。**
- **病根**：我们只在**候选核验**里剥音轨号（`MakeTitleCandidates` 里那条策略），
  **搜索词里没剥** —— 于是第一关就搜错了东西，后面两道闸门再准也救不回来。
  日志表现成「过曲名闸 0 条」，看起来像"网易云没有这首歌"，**其实是"我们搜错词了"**。
  这类"看起来像 A、实际是 B"的日志措辞，是这次排查里最花时间的地方。
- **修法**：导出 `StripLeadingTrackNumber()`（复用匿名的 `CollectTrackNumberStripped`，
  **不另写一套切法** —— 两处切得不一样就会出现「搜索按 A 切、核验按 B 切」的
  自相矛盾），搜索词用它。
- **⚠️ 但剥法是「≤3 位数字 + 分隔符」，挡不住以数字开头的真曲名**：
  `7 Years` -> `Years`，`99 Problems` -> `Problems`。
  - 这在**本地搜索**里无害 —— 那里只是**多**一个候选，原样的还在；
  - 在**搜索词**里有害 —— 那是**替换**。
  - 所以 `TryNetEase` 变成**两趟**：先拿剥过的词搜，没搜到可用候选就用**原词**再搜一次。
    只有真的剥掉了什么才走第二趟，代价是一次额外请求。
- **我自己写测试时踩的**：断言写的是「`7 Years` 不该被剥」，被单测直接打回来 ——
  这条能力边界现在是**断言**（记录边界，不是记录缺陷），实现靠线上后路兜。
- **测试**：233 → **252 条，全过**。
- **验证**：装机 hash `0050D35BAF87EA41`（守候进程自动装的，第 4 次）。

## D-040 「缓存到本地的歌词还没有第一行的分隔线」—— 分隔线挪到取词的统一出口

- **起因**：用户说「呃，缓存到本地的歌词还没有第一行的分隔线」。
- **病根很清楚**：分隔线原来补在 `StripNetEaseCredits` 里，而那只覆盖
  **本次从网易云新取到的词**。缓存里的 `.lrc` 是**上一次写下的**，
  根本不会再走那段代码。
- **修法**：把「前奏补分隔线」抽成 `EnsureLeadInSeparator()`，挂在**取词的统一出口**：
  - `SaveAndReturn`（新取到的词，写缓存前）
  - 缓存命中路径（读出来的词）
  两条路走同一个函数、同一条规则。**幂等**（首行已经是线就不再加），
  所以新写的缓存（已带线）和旧缓存（没带线）都安全。
- **顺手确认了写缓存的文本**：`SaveAndReturn` 里 `WriteWholeFile(paths.lrc, text...)`
  用的正是补过线的 `text`，所以**今后的缓存文件自带分隔线**，读出来时那一步是空转。
- **用真实缓存数据确认了对症**（这一步值得做 —— 不然只是"觉得应该有用"）：

  | 缓存文件 | 行数 | 首行时间戳 |
  |---|---|---|
  | `059e7b81bf6e` | 35 | `[00:25.16]` |
  | `5f259ddef0b8` | 52 | `[00:20.15]` |
  | `6405b4c30781` | 39 | `[00:31.35]` |
  | `60f613362dc7` | 44 | `[00:29.30]` |
  | `8fe7ae28cb4b` | **5** | **`[00:58.17]`** |

  **每一条都是 20~58 秒才起头。** 最后那个尤其说明问题：一首只有 5 行「啦啦啦」的歌，
  前 58 秒面板都把第一句当成"当前行"在提前高亮。
- **不需要清缓存**：补线在**读**的时候做，旧 `.lrc` 原样留着就行，
  也就不用为此重新联网（那会撞上限流）。
- **测试**：新增 `TestLeadInSeparator`（幂等、首行在 0 秒不补、畸形时间戳不猜、

## D-039 守候进程改成「盯编译产物」的常驻模式（原来那个「等播放器退出」已经过时）

- **起因**：用户说「以后都启动一个守候进程，更新简单一点」。
- **原来那个模式为什么过时**：`watch-install.ps1` 原本是
  「等播放器退出 → 拷贝 → 可选重启」。它存在的**唯一理由**是绕开
  foobar2000「立即重启」那个约 1 秒的空档（旧轮询周期约 900ms，整个跳过去了，
  结果是装了旧版还一声不吭 —— 见脚本头部那段注释）。
  但 `hot-install.ps1` 的改名方案**根本不依赖那个时间窗口**，
  脚本自己的注释里就写着「热安装根本不依赖那个时间窗口：什么时候跑都行」。
  **守候进程该盯的不是「播放器退出了没」，而是「编译产物变了没」。**
- **改法**：同一个文件名，改成**常驻**：
  - 轮询 `bin\x64\Release\foo_lyricus.dll` 的哈希，变了就调 `hot-install.ps1` 装；
  - 「已装版本」的判据取**目标文件**的哈希，不是自己记的状态 ——
    这样中途有别人装过也不会重复劳动；
  - `-Once` 装一次就退；`-Relaunch` 装完自动重启播放器（默认**不**重启 ——
    会打断听歌）；`-IntervalMs` 调轮询周期；
  - 单实例锁沿用原来的机制。
- **⚠️ 一个不能省的细节：必须等编译写完。**
  判据是「**大小 + 修改时间连续两次采样都不变**」，不能只看哈希变了就动手 ——
  链接器写到一半时哈希也是"变了的"，那时拷过去会装上一个**半截的 DLL**，
  而且 **`hot-install.ps1` 的哈希校验查不出来**（源和目标是同一份半截，
  两边哈希当然一致）。这是整个脚本里最容易想漏的一处。
- **顺手加的**：`Say` 同时写一份 `build\watch-install.log`。
  常驻进程的输出事后要能查，而 `Write-Host` **不走标准输出重定向**，
  所以不能指望 `Start-Process -RedirectStandardOutput` 把隐藏窗口的内容捞出来。
- **验证**（真跑了一遍，不是只看代码）：
  ```
  [21:51:35] 发现新构建 791,040 B  86389289E55B6253
      [21:51:36] 已把在用的旧版改名让路（镜像锁绕过了）
      [21:51:36] 已安装: …\foo_lyricus.dll
  [21:51:36] 第 1 次安装完成。重启播放器后生效。
  ```
  编译完 1 秒内自动接住，装完的哈希与构建产物一致。
- **注意**：装上去之后**运行中的播放器仍执行内存里的旧代码**，新版要下次启动
  才生效 —— 这是 foobar2000 的模型（组件不能运行中重载），不是脚本的问题。
  想让这一步也自动化就加 `-Relaunch`。

## D-038 剥掉名单后补一行**分隔线**（不是空行）—— 以及「别随便动 parser」

- **起因**：用户说「你把工作室信息去掉没有错，不过应该加上一行空歌词，这样会好一点」。
- **病根**（`lyric.cpp:171`）：
  ```cpp
  size_t LyricDocument::LineIndexAt(double t) const {
      if (t < m_lines.front().timeSec) return 0;   // ← 返回**第一行**
  ```
  「第一条时间戳之前」一律算成第一行是当前行。剥掉名单后歌词从 `[00:29.260]`
  才开始（名单占到 `[00:27.010]`），于是**前 29 秒里第一句真歌词一直被当成
  "当前行"高亮着** —— 明明还没唱到。
- **第一版做法是错的，已回退**：直接改 `Parse()`，在第一行时间戳 > 0 时插一行空行。
  **一次打挂 26 条解析断言**（行数、时间戳、编码全对不上）。
  更根本的问题：**解析器不该凭空造行**，解析结果必须等于文件内容。
- **用户当场给了更好的方向**：「或者换成分隔线。随便动 parser 可能会有解析问题。」
  —— 判断完全正确。
- **最终做法**：在 `StripNetEaseCredits` 里用**第一个被剥掉的时间戳**补一行
  `[00:00.000]———`。
  - 分隔线是**一行有文字的普通 LRC**，现有解析器原样接受；
  - **`lyric.cpp` / `lyric.h` 一行都没动**（已用 `git diff HEAD` 核对为零差异）；
  - 视觉结果和"空行"一样：前奏期间当前行是这条线，真歌词作为**下一行**在下面等着。
- **为什么不能真的用空行**：`Parse()` 明确**丢弃空文本行**
  （`lyric.cpp`：夹具里歌词之间夹着空行，不能渲染成空行）。
  想用空行就必须改那个丢弃逻辑，而它是全工程共用的。
- **踩到的两个坑**：
  1. **补分隔线必须在"判空"之后。** 整篇都是名单的条目（纯音乐，网易云上很常见）
     剥完是空的，本该返回空让面板显示「（无歌词）」；先补分隔线的话 `out` 就非空了，
     会被当成"有歌词"，整首歌显示一条横线 —— **比一片空白更让人困惑**。
     这个 bug 是断言 `整篇都是名单 -> 返回空` 抓出来的。
  2. 分隔线用 `WideToUtf8(L"———")` 而不是直接写窄字符串字面量 ——
     后者对不对取决于工程的源码/执行字符集设置（`/utf-8`），换个构建配置就可能乱码。
- **样式可换**：`NetEaseIntroSeparator()` 一个函数，改一行即可
  （候选：`———` / `♪` / `· · ·`）。
- **测试**：228 → **233 条，全过**（新增 5 条守着分隔线的位置、带文字、
  以及"没剥过就不该多出一行"）。
- **验证**：已装机 hash `8B8D49646A5A9B5F`。

## D-037 撞到墙就别再撞：网易云限流的进程级冷却

- **起因**：D-036 装好之后用户说「再看日志」。日志证实**修复生效了** ——
  405 被正确识别、自动重试、`本轮不写未命中标记`、v3 旧标记也作废了：
  ```
  未命中标记是旧匹配逻辑（v3，当前 v4）写的，已作废并重新联网查询
  网易云返回业务码 405，800 ms 后重试（第 1 次）
  网易云返回业务码 405，1600 ms 后重试（第 2 次）
  网易云返回业务码 405，2500 ms 后重试（第 3 次）
  网易云业务码 405（HTTP 200）—— 本轮不写未命中标记
  ```
- **但暴露了下一层问题**：限流**持续了两分钟以上**（00:47:28 → 00:49:27 全 405），
  而我们的重试窗口只有 5 秒。于是**每次换曲白烧 ~5.3 秒**在注定失败的重试上，
  再去查 LRCLIB（对这批同人曲基本是空的）—— 一次换曲白跑 **9.5 秒**后台。
- **同一个日志里还有一条正面证据**：`05 虚无之人` **走缓存成功载入了 37 行**。
  说明网易云的匹配逻辑在没被限流时是好用的，问题纯粹在请求纪律。
- **修法**：
  1. **进程级冷却**：撞到 405 就记下"封禁到这个时刻"，期间**直接跳过网易云**
     （不发请求、不重试），转去 LRCLIB。连续撞到指数加长：60s → 120s → 240s，
     上限 10 分钟。用 `std::atomic`（查询在后台线程，可能同时好几个）。
  2. **最小请求间隔 1200ms**：快速连点切歌时会连着发请求，
     这多半就是触发限流的原因之一。同一瞬间不挤进多个请求。
  3. 冷却期间仍然 `requestFailed = true` —— 是"没问出来"，**绝不**写未命中标记。
  4. 冷却期间只记一条日志，不每次换曲都刷屏。
- **限流是我自己触发的**：为了看候选连打了三十几次搜索接口，把用户的环境
  一起限进去了。**这条教训比代码本身重要** —— 见 D-036 的"教训"一节。

## D-036 网易云把错误码放在**响应体**里（HTTP 200 + code 405）—— 限流被记成了 7 天的假「没有」

- **起因**：用户反馈「还是有一些没识别出来」。
- **诊断日志先给了方向**（D-035 加的过闸计数这次直接派上用场）：
  ```
  网易云候选核验 —— 过曲名闸 3 条，其中时长对上 0 条、演唱者对上 0 条，可用 0 条
  网易云候选核验 —— 过曲名闸 0 条，其中时长对上 0 条、演唱者对上 0 条，可用 0 条
  ```
- **但真正的元凶是在我自己探测接口时撞出来的**：
  ```json
  HTTP/1.1 200 OK
  {"msg":"操作频繁，请稍候再试","code":405,"message":"操作频繁，请稍候再试"}
  ```
  **网易云把业务错误码放在响应体里，HTTP 状态码仍然是 200。**
- **于是整条链路错得很自然**：
  1. 我们只看 `search.status`（200，正常）；
  2. `ParseNetEaseSearchRoot` 找不到 `songs` 键 → 判定「这首歌网易云上没有」；
  3. `requestFailed` 保持 false → 转去 LRCLIB；
  4. LRCLIB 也没有 → **写下 7 天有效的未命中标记**。
  日志里「搜索无结果（响应里没有 songs 数组）」就是限流的签名，实测出现 **4 次**。
- **还有一个连带问题**：`HttpGet` 的退避重试是**基于 HTTP 状态码**的
  （`ShouldRetry`），所以 405 **永远不会被重试** —— 限流了就直接认输。
- **修法**：
  1. `ParseNetEaseCode()` 解析响应体里的 `code`。用 `rfind` 取**最后一个**
     `"code"` 键，避开嵌套对象里的同名字段（响应形状是 `{"result":{...},"code":200}`）。
  2. 搜索和歌词**两个接口**都要查业务码 —— 歌词接口同样会返回限流响应，
     漏掉的话会把限流当成「这首歌是纯音乐」。
  3. 在 `TryNetEase` 里加一层**业务码重试**（800/1600/2500 ms，最多 3 次），
     因为 `HttpGet` 那层对 405 不生效。
  4. 任何非 200 的业务码 → `requestFailed = true` → **绝不写未命中标记**。
- **`kMissLogicVersion` → 4**：v3 期间写下的「没有」里混着限流造成的假结论，
  必须全部作废重查。这是这个版本号第三次救命。
- **教训**：
  - **「HTTP 200」不等于「成功」**。第三方接口把错误码放在 body 里是常见做法，
    只看状态码会把「没问出来」和「确实没有」混为一谈 —— 而这两者的后果天差地别
    （前者该重试，后者该缓存）。
  - **退避重试要盖住所有"暂时性失败"的形态**，不只是 HTTP 状态码。
  - 调试时**自己也会触发对方的限流**：我为了看候选连打了几十次搜索，
    结果把用户环境也一起限流了。以后探测要节制。
- **测试**：218 → **228 条，全过**（新增 `TestNetEaseBizCode`，
  含"嵌套对象里的 code 不能抢走顶层的""字符串形式的码宁可当失败"）。
- **验证**：已装机 hash `B39CDC44EF0BE0F3`。

## D-032 模糊匹配重写（零分配 + 查询侧只算一次）；以及「慢日志量到的不一定是我们的代码」

- **起因**：D-031 之后用户反馈「好一点了」—— 不是「好了」。读日志发现新版会话里
  只剩一条慢记录，而且是换曲路径：
  ```
  慢: FindLyricFile（目录搜索） 用了 11.5 ms
  慢: ReloadLyrics（搜索+加载） 用了 11.9 ms
  慢: OnNewTrack（换曲主线程） 用了 12.8 ms
  ```
- **先建基准再动手**（`tests/harness/bench_search.cpp`，`run.ps1 -Suite bench`）。
  这一步是关键：**没有基准就只能猜**，而我一开始就猜错了（见最后一条）。
  改动前的实测：

  | 目录里的歌词文件数 | 平均耗时 |
  |---|---|
  | 0 | 0.055 ms |
  | 50 | 0.900 ms |
  | 500 | **7.07 ms** |
  | 3000 | **42.7 ms** |

  每个文件约 **15 µs**，完全线性 —— 所以「每张大一点的专辑都会有」这个描述是对的。
  关掉模糊匹配后 3000 文件从 43.1ms 掉到 12.7ms：**模糊占 70%**。
- **病根**（`FuzzySimilarity`，原来是自由函数、逐文件调用）：
  ```cpp
  std::vector<std::wstring> ba, bb;
  CharBigrams(a, ba);   // 每个二元组一个 std::wstring：20 字曲名 = 19 次堆分配
  CharBigrams(b, bb);   // 每个文件都重算
  std::sort(ba.begin(), ba.end());   // 排序字符串
  std::set_intersection(...);        // 再分配一个结果 vector
  ```
  **而且 `a` 是查询串、整个目录扫描里根本不变，却每个文件重算一遍** ——
  一半计算量是纯重复。
- **改法**（相似度公式与阈值**一字未改**，所以命中结果逐条一致）：
  1. 二元组打包成 `uint32_t`（高 16 位 + 低 16 位两个 UTF-16 码元）——
     整个相似度计算**一次堆分配都不需要**，排序从比字符串变成比整数。
     排序顺序变了不影响结果：`set_intersection` 只要求两侧用同一个序。
  2. 做成 `FuzzyMatcher` 对象：query 的二元组构造时算一次并排好序，全程复用；
     候选侧的缓冲也复用。
  3. 交集只数个数，手写双指针，替掉 `set_intersection` + `back_inserter`。
- **改后**：

  | 文件数 | 改前 | 改后 | |
  |---|---|---|---|
  | 500 | 7.07 ms | **2.38 ms** | 快 3.0× |
  | 3000 | 42.7 ms | **16.1 ms** | 快 2.7× |
  | 每文件边际 | 15.2 µs | **5.7 µs** | |

  剩下的成本已经不在模糊上（模糊从 30ms 降到约 1~3ms），而是目录枚举 + 每文件一次
  `NormalizeLyricStem`（约 1 µs）。138 条断言全过。
- **⚠️ 这一条比上面的优化更重要 —— 一个差点让我改错方向的教训**：
  那 11.5ms **根本不是我们的代码慢**。
  基准跑在 C:（SSD）上，而日志里是 F:（WD My Passport，外置 USB + exFAT），
  于是加了「在真实目录上量」的模式，200 次实测：

  ```
  F:\thoughts        中位 0.184   p95 0.240   最慢 0.500 ms
  F:\The Silent...   中位 0.218   p95 0.309   最慢 0.676 ms
  ```

  **最慢也没超过 0.7ms。** 也就是说 `ScopedTimer` 报的 11.5ms 里，
  绝大部分是**主线程被抢占**的墙上时间，不是我们花掉的 CPU。
  那一刻日志里确实有**两个在线查询正在跑**（00:01:58 和 00:02:11 发起），
  各自在做 WinHTTP 重试、退避 Sleep、写缓存文件。
  **`ScopedTimer` 量的是墙上时间 —— 看到"慢"要先问一句"这时间真是我花的吗"。**
- **顺带发现的一个真问题（用户决定暂不修）**：被顶掉的在线查询**没有取消机制**。
  日志里 00:01:58 发起的查询一直跑到 00:02:24，白跑 26 秒网络，
  最后只留下一句「结果已过期（期间换过曲），丢弃」。
  `m_onlineGeneration` 只在**查询结束后**检查，过程中完全不知道结果已经没人要了。
  快速切歌会把这些任务堆起来（每个最多重试到 ~25s），
  正是主线程被抢占的来源。
  修法很清楚（`HttpGet` 的重试循环里有干净的检查点），
  但有个**权衡**：取消会丢掉本该写进缓存的结果 ——
  用户下次播到那首歌又得重查一次。
  **2026-09-24 用户拍板：先不做，用一阵再说。** 已记进 `docs/plan.md` 的待解决表（#8），
  别当成新问题重新查一遍。

## D-031 「拖进新专辑会卡一会」的定位：不是换曲慢，是面板每 250ms 重绘太贵

- **起因**：用户报「拖进来新的专辑之后会卡一会」「每张大一点的专辑都会有这样的情况」。
- **第一轮假设（错）**：以为是换曲时读标签 + 搜歌词太慢。为此加了 `ScopedTimer`
  埋点（`OnNewTrack` / `ReloadLyrics` / `RenderTagField` / `FindLyricFile`）。
- **埋点数据推翻了它**：跑了一整天，**一条 `慢:` 的换曲记录都没有** ——
  连那首无标签的 168MB WAV 也不慢。上一轮抓到过一次 21.7ms，但复现不了。

  真正持续在慢的是这个，成对出现、刷了几十次：
  ```
  慢: RenderLayered（重建 DIB + 提交） 用了 5~13 ms
  慢: 面板定时器一拍 用了 5~9.5 ms
  ```
- **为什么每拍都重绘**：`RefreshPosition()` 只要播放位置变了就返回 true，
  而播放时位置**每拍都在变**（进度条要动）。也就是说面板**每秒重绘 4 次**，
  每次 5~7ms —— 主线程每秒被占掉 20~28ms，**持续不断**。
  拖专辑时 foobar2000 自己正在大量读标签、更新列表，我们的重绘正好和它抢主线程。
- **查证**：我们**没有**注册任何 `playlist_callback` / metadb 钩子，
  `play_callback` 也只挂了 `new_track | stop | starting` 三个 flag ——
  拖专辑这个动作**根本不经过我们的代码**。所以唯一的贡献就是那个 4Hz 重绘。
- **每一帧都在重复做、而本可以复用的事**：
  | 每帧重复 | 代价 |
  |---|---|
  | `CreateFontW` × 4（曲名 / 当前行 / 普通行 / 时间） | 要解析字体名、查字体库 |
  | `CreateDIBSection` + `DeleteObject` 一张 920×300 位图（约 1.1MB） | 分配 + 释放 |
  | 每行 `DrawTextW` 量 2~3 次（`MeasureLine` 探路 + `DrawLine` 里再量） | 每次都是一遍文本整形 |
- **修法**（三处，都是"尺寸/参数没变就复用"）：
  1. `MakeFont` 按 `(dpi, 字号, 粗体)` 缓存 HFONT，进程内不释放。导出
     `GetCachedUiFont()` 给渲染层以外的绘制代码共用。
  2. `RenderLayered` 缓存 DIB + 内存 DC，只在窗口尺寸变化时重建
     （`ReleaseLayeredCache()`，在 `WM_DESTROY` 里释放）。
  3. 单行高度按 `(HFONT, 文本)` 缓存 —— `DT_SINGLELINE` 不换行，
     高度只由字体决定，与 `maxWidth` 无关，所以键取到 `(字体, 文本)` 就已经精确，
     命中与现场重算**完全等价**，排版不变（`test_view` 那 15 条按像素带验证的断言全过）。
  4. **把"画的次数"降下来**（这一条其实最根本，见下）。
- **第 4 条的来龙去脉**：用户看到前三条后说「为此开个多线程好像有点不太划算」。
  这个判断是对的，而且多线程在这儿**技术上就别扭**：
  `UpdateLayeredWindow` 是窗口操作、必须在窗口所属线程调用，工作线程只能准备 DIB、
  提交还得回主线程；渲染要读 `PlaybackState`（主线程状态）得加锁或快照；
  GDI 自己还有一把堆锁，两个线程同时 `DrawTextW` 会互相抢。**未必更快。**
  真正该省的是**画的次数**，而这里恰好有一大块白烧的：
  `RefreshPosition()` 原来返回一个 bool，把「换行」和「位置在走」混在一起 ——
  而播放时位置**每 250ms 都在变**，于是每拍都全量重画。
  但位置变化只影响进度条和时间文字：进度条在 4 分钟的曲子上
  **每秒才走约 1 个像素**，也就是说 4Hz 里有 3 次画出来的画面和上一次**一模一样**；
  时间文字本来也只每秒变一次。
- **做法**：`RefreshPosition()` 改返回 `TickChange{None, Position, Line}`，
  三个宿主只在 `Position` 且距上次位置重绘满 `kPositionRepaintMs`（1000ms）时才重绘；
  换行 / 换曲 / 改设置 / 用户拖动**不受节流**，各自仍有独立触发条件、立刻重绘。
  1Hz 是「信息一点都不丢」的上限。
  `kPositionRepaintMs` 放在 `playback_state.h` 而不是各宿主里 ——
  三个宿主烧的是同一条主线程，没有理由各不相同。
- **踩到的坑**：底图缓存了就不能再删字体（见上）；另外 `TickChange change` 这个变量名
  一开始叫 `tick`，和三个宿主里都有的 `ScopedTimer tick(...)` 撞名，编译直接报
  `C2373 重定义；不同的类型修饰符`。
- **验证**：138 条单元断言全过，排版与修改前逐像素一致；已装机 hash `1CCB46865E7C42C3`。
- **还留着的**：两个 27 万像素的循环（铺底那个可以把 4 次写 1 字节改成一次写 4 字节）。
  但按上面的账，节流之后它们的绝对占比已经不高了 —— 先测，别盲改。
- **踩到的坑**：缓存了字体就**绝不能再 `DeleteObject`**。`DrawLyricsView` 原来在
  末尾删 `fHeader/fCurrent/fBody`、`DrawControls` 删 `fSmall` —— 不删掉这几行，
  缓存里立刻就是野句柄，下一帧 `SelectObject` 拿到的是已释放的 GDI 对象。
- **明确不走的路**：不为渲染开线程。理由见上面第 4 条。
- **验证**：138 条单元断言全过，排版与修改前逐像素一致。

## D-030 浮动面板外观可配置；嵌入面板继续跟随宿主主题

- **起因**：用户问「这个窗口的颜色或者其他属性支不支持用户自定义」。
  查下来现状是分裂的：
  | 面板 | 配色来源 |
  |---|---|
  | 浮动面板 | 源码里**写死** |
  | DUI 元素 | 跟随默认 UI 配色 |
  | CUI 面板 | 跟随 Columns UI 配色 |

  **用户实际每天在用的浮动面板，恰恰是唯一不能改的。**
- **边界**：用户明确说「是浮动面板，内嵌式的不去管他」。
  这也符合设计 —— 嵌入面板**本来就该**跟随宿主，用户在 foobar2000 里改配色、
  面板跟着变才是对的；给它们另设一套反而割裂。
- **做法**：
  * `PanelAppearance`（config.h）：6 个颜色 + alpha，默认值就是原来的硬编码值。
  * **首选项页**（`prefs_page.cpp` + `lyricus.rc` + `resource.h`）：
    6 个色块按钮（点开系统取色器）+ 一个不透明度滑块 + 恢复默认。
  * 菜单那条命令从「材质两态切换」改成**通透度四档循环**（100/95/85/70%）。
  * 浮动面板每 250ms 轮询这份配置 —— 和显示设置同一套机制，
    首选项页和面板之间**没有任何回调耦合**（页面销毁不会影响面板，反之亦然）。

- **踩到的坑（都有代表性，记下来）**：
  1. **工程第一次有 `.rc`**。`preferences_page_impl<TDialog>` 要求 TDialog 能
     `Create(parent)`，也就是必须基于对话框资源（helpers/atl-misc.h:271-280）。
  2. **rc.exe 默认按系统代码页读源文件**，UTF-8 的中文会乱码。
     正解是 `#pragma code_page(65001)`。
  3. **模态取色器会泵消息**，期间首选项窗口可能被关掉、页面随之被释放 ——
     SDK 在 `preferences_page.h:133` 专门警告过。解法是进 `DoModal` 前
     **拿一份自身引用把自己钉住**（`service_ptr_t<preferences_page_instance> self = this;`），
     返回后再 `::IsWindow` 确认窗口还在。
  4. **WTL 消息宏的处理函数签名必须逐条核**（atlcrack.h）：
     第三参是**裸 `HWND`**，不是 `CWindow`；`MSG_WM_HSCROLL` 传的是
     `(int, short, HWND)` 不是 `(UINT, UINT, CScrollBar)`。
     凭印象写会得到「函数不接受 N 个参数」这种看不出所以然的错。
  5. **ATL 的 `CWindow` 成员会遮蔽同名 Win32 API** ——
     `InvalidateRect` / `IsWindow` / `SendMessage` 在成员函数里不加 `::`
     会被解析成成员版本，参数对不上就报错。全部加 `::` 解决。
  6. **渲染前先取配置快照**。不 `const` 一份本地副本的话，
     用户在另一头拖不透明度滑块时，铺底和 alpha 修正会读到不同的值，画面会花。

## D-029 菜单里不该出现明知不可用的选项 —— 「切换背景材质」的教训

- **用户报的问题**：「点击切换背景的时候会改变样式，变成不透明的。」
- **日志还原的经过**（一晚上踩了两次）：
  ```
  [23:12:09] 菜单：切换背景材质 -> 无（不透明）   ← 第一次点，掉进去
  [23:12:13] 菜单：切换背景材质 -> Mica
  [23:12:20] 菜单：面板已重置                     ← 只能用「重置」救回来
  [23:15:58] 菜单：切换背景材质 -> 无（不透明）   ← 又点一次，又掉进去
  [23:16:32] 菜单：面板已重置                     ← 又用重置救
  ```
- **三个问题叠在一起**：
  1. **循环里混着 3 个坏模式**。D-009 早就查明 Mica / Acrylic / Mica Alt
     与 GDI 绘制不兼容（API 返回 `S_OK`，但画面根本不呈现）。
     它们却一直留在这条命令的循环里 —— **菜单提供了明知不可用的选项**。
  2. **顺序刚好最坑**：`无 → Mica → Acrylic → Mica Alt → 半透明`，
     而默认是「半透明」，所以**点一下正好跳到最差的「无（不透明）」**。
  3. **没有直接回去的办法**。唯一的退路是「重置面板位置与材质」，
     而它**顺带把面板位置也重置了** —— 用户为一件事付了两件事的代价。
     日志里 `ComputeInitialRect: 无保存位置` 就是这么来的。
- **修法**：
  * 这条命令**只在能用的两种之间切换**：`半透明（自绘）` ⇄ `无（不透明）`。
  * 菜单名带上当前值（`切换背景材质（当前：半透明（自绘））`），
    和字号/行数/位置那几条保持一致。
  * `ApplyBackdrop()` 里加兜底：配置里若存着那三种材质，**启动时自动降级**
    并记一笔日志 —— 否则面板会每次启动都空白，而菜单还显示"设置成功"。
- **通用教训**：**别把"暂时不行"的东西留在用户可点的位置上。**
  开发期的对比开关（"方便现场对比效果"）在交付后就变成了纯粹的陷阱：
  用户不知道哪个能用，点进去看到的是坏状态，还得自己摸索怎么出来。
  该删就删，或者至少别放在默认值旁边。

## D-028 纯逻辑用「shim 单测台」验，不要每次都劳烦播放器

- **动机**：真机联调（造静音夹具 → 让播放器播 → 读日志）能验端到端链路，
  但**每验一个边界条件就要播一次音频**，慢，而且会打断用户。
- **关键观察**：这个工程里最容易出错的两块 —— 歌词搜索和 LRC 解析 ——
  **都是纯函数**：
  * `FindLyricFile()` 是**对文件系统的纯函数**（给音频路径，返回歌词路径）
  * `LyricDocument::Parse()` 是**对字节数组的纯函数**（给字节，返回文档）

  两者都不需要 foobar2000 宿主，直接调就行。
- **做法**：`tests/harness/` 里放两个替身头文件（`stdafx.h`、`<SDK/cfg_var.h>`），
  把真实源码**逐字节复制**到临时目录配它们一起编译，跑完即弃。
  `run.ps1` 一条命令跑完两组（搜索 25 项 + 解析 39 项）。

  **为什么是"拷过去"而不是 `-I` 指过去**：头文件用引号包含时
  **优先在包含者所在目录**找，替身 `stdafx.h` / `config.h` 根本塞不进去。
  拷的是逐字节副本，不存在"测的是另一份代码"的问题 ——
  `config.h`、`lyric.h`、`lyric_search.h`、`debug_log.h` 用的都是真实那份。

- **分层结论（以后照这个来）**：
  | 要验的东西 | 用什么 |
  |---|---|
  | 算法、边界、编码、打分 | **shim 单测台**（毫秒级，不打扰任何人） |
  | 端到端链路（联网、缓存、渲染、宿主集成） | 静音夹具 + 真机（见 D-024/D-027） |

- **收获**：LRC 解析器 39 项**一次全过**，包括编码识别（UTF-8 有无 BOM /
  UTF-16LE / GB18030 兜底）和 `[offset:]` 正负 —— 这些是"判错了整屏乱码、
  而日志一句话都不说"的地方，光靠真机联调极难覆盖全。

- **覆盖现状（2026-09-23）**：三组共 **118 项断言，0 失败**。

  | 组 | 断言 | 测的是 |
  |---|---|---|
  | 搜索算法 | 25 | 四条策略打分、候选切分、归一化、extraDir 优先级 |
  | LRC 解析器 | 39 | 编码识别、小数位缩放、多时间戳、offset、`LineIndexAt` 边界 |
  | 在线歌词 JSON | 54 | 转义、代理对、`null` vs 缺失、畸形容错、百分号编码、缓存键 |

- **一个值得记住的手法**：`online_lyric.cpp` 的解析函数全在**匿名命名空间**里，
  外部链接不到。但测试台本来就要把源码拷到临时目录，
  所以测试文件直接 `#include "online_lyric.cpp"` 就把它们并进了同一个翻译单元 ——
  **匿名命名空间的名字立刻可见**，而测的仍是同一份源码。
  代价是这个 .cpp 不能再单独参与编译（会重复定义），`run.ps1` 里为此单独标注了。
  这个手法让"手写 JSON 解析器"这种内部实现也能被单测覆盖。

## D-027 在线歌词的核对不能只比曲名原文 —— 无标签文件的 `%title%` 会退化成文件名

- **背景**：D-024 定下「`/api/search` 会张冠李戴，调用方必须核对」。
  核对的第一条是**曲名归一化后必须相等**。
- **怎么发现的**：造了一个**静音**夹具 `周杰伦 - 晴天.wav`（270 秒，对齐 LRCLIB），
  真机跑在线查询。日志：

  ```
  /api/get 未命中（404），改走搜索
  第 1 次尝试失败（HTTP 503），600 ms 后重试      ← 重试逻辑被真实 503 验证
  第 2 次尝试失败（HTTP 503），1500 ms 后重试
  共尝试 3 次，最终 HTTP 200
  /api/search 返回 20 个候选
  命中 id=7976416（用 syncedLyrics，2045 字节）｜匹配到：周杰伦 - 晴天（270.0 秒）
  结果与当前曲目对不上，丢弃。在线=[周杰伦 - 晴天, 270.0s]  本地=[ - 周杰伦 - 晴天, 270.0s]
  ```

  **它找到的完全正确，却被核对逻辑丢掉了。**

- **根因**：夹具没有标签，于是 foobar2000 的 `%title%` 退化成**文件名**
  `周杰伦 - 晴天`，而 LRCLIB 的 `trackName` 只有 `晴天`。精确比对必然不等。
- **为什么这是必须修的**：用户曲库里「文件叫 `Artist - Title.wav` 而没有标签」
  **非常常见**（本次实验用的就是这个形态，纯属巧合地撞上了真实情形）。
  不修的话，**所有无标签曲目的在线歌词都会被静默丢弃**，
  而且日志里只会说"对不上"，看起来像是 LRCLIB 数据不准 —— 极易误判。
- **修法**：核对时拿「去前缀」切分后的**全部候选**去比，
  并且**复用搜索模块内部那一份切法**（新暴露 `MakeTitleCandidates()`），
  不另写一套 —— 两处切法不一致会造出「搜索按 A 找到了、核对按 B 又否掉」
  这种自相矛盾。
- **顺带确认到的（同一轮测试）**：
  * `503` 重试路径在**真实 503** 上工作正常（LRCLIB 当时确实过载）；
  * 缓存落盘正常：`.lrc`（2,045 B）+ `.meta`（118 B）两个文件都在；
  * 「本地搜索未命中 → 排队等时长 → 发起在线查询」这条时序链路完全按设计走。

> **测试方法值得记下来**：造**静音** WAV 当夹具，时长对齐 LRCLIB 的返回值。
> 这样能在**不发出任何声音**的前提下跑完整的在线查询链路 ——
> 半夜测、用户正在用电脑时测，都不打扰人。

## D-026 热安装：Windows 允许给**已加载的 DLL 改名**，于是不用关播放器就能换组件

- **背景**：组件 DLL 被 foobar2000 加载后就被锁住，不能覆盖也不能删除。
  于是每次迭代的固定动作是「关播放器 → 拷贝 → 开播放器」，
  还专门写了 `watch-install.ps1` 来守候退出。

- **踩的坑**：守候脚本靠轮询 `Get-Process` 判断播放器是否退出。
  但 foobar2000 自己的「**立即重启**」（改 UI 设置时会弹）只停机约 1 秒，
  而 700ms 的轮询加上 `Get-Process` 自身开销、实际周期接近 900ms ——
  **整个空档被跳过去了**。现象极具迷惑性：播放器明明重启了，
  装的还是上一版 DLL，而且守候进程一声不吭地继续傻等。
  （第一次修是把轮询降到 150ms 并改成循环等待，但本质上还是在赌时间窗口。）

- **真正的解法**：**Windows 不允许覆盖/删除已加载的镜像，但允许给它改名。**
  镜像节是以 `FILE_SHARE_DELETE` 打开的，目录项可以动，映射不受影响。
  所以：
  ```
  把 foo_lyricus.dll 改名为 foo_lyricus.dll.old   <- 绕过镜像锁
  把新编译的拷成 foo_lyricus.dll
  按哈希复核
  ```
  **全程不需要播放器退出。** 实测通过（2026-09-23）。

- **代价**：运行中的播放器**仍然执行内存里的旧代码**，新版要下次启动才生效。
  这不是缺陷 —— 组件本来就不能在运行中重载，这是 foobar2000 的模型。
  好处是：此后**任何一次**重启都会加载到新版，不再依赖"抓住那个 1 秒的空档"。

- **产物**：`tools/hot-install.ps1`（带完整回滚：改名后拷贝失败会把 `.old` 改回去）。
  `watch-install.ps1` 保留 —— 需要「装完自动重启」时还有用。

- **通用教训**：**「文件被占用」不等于「什么都做不了」。**
  先问一句"到底哪一步被禁止了"，再决定要不要绕。这里的答案很具体：
  禁止的是覆盖和删除，不是改名。

- **补记：这个脚本第二次用会失败，原因比上面更绕。**
  备份名原本固定用 `foo_lyricus.dll.old`。但上一次热安装改名后的那个 `.old`，
  **正是播放器此刻正在执行的镜像** —— Windows 对已加载镜像的改名是
  "文件对象跟着新名字走"，所以 `.old` **自己也被锁着**，既删不掉也覆盖不了。
  于是第二次运行必然报「当文件已存在时，无法创建该文件」，
  而且看起来像是"这条路在当前环境走不通"，极易误判。

  **修法**：备份名带时间戳（`foo_lyricus.<yyyyMMdd-HHmmss>.old`）。
  后缀刻意**不以 `.dll` 结尾**，免得被 foobar2000 当成组件加载。
  另外加了一段清理：更早的备份能删就删，正在执行的那份删不掉就静默跳过。

  **教训**：涉及"改正在使用的文件"的工具，要**至少连续用两次**再宣布它可用。
  第一次成功说明不了什么 —— 状态是第一次自己造出来的。

## D-025 用 `>= 0` 判断「有没有保存过坐标」是错的 —— 副屏坐标可以是负的

- **代码**：`control_window.cpp` 的 `ComputeInitialRect()`
  ```cpp
  if (sx >= 0 && sy >= 0) {     // ❌ 错
  ```
- **为什么错**：`config.h` 里 **`-1` 才是「从未保存过」的哨兵值**
  （`cfg_panel_x` / `cfg_panel_y` 的初值就是 -1）。
  而主显示器**左边或上边**的显示器，其 X / Y 坐标本来就是**负数**。
  用 `>= 0` 判断，就把「面板放在左侧副屏」这种完全合法的位置
  当成了「没保存过」。
- **现象**：每次启动面板都跳回主屏居中，用户以为"位置没记住"。
- **怎么发现的**：**装上去真跑**才暴露的。
  之前的会话里面板恰好停在正坐标（1901,67），日志显示"沿用已保存位置"，
  一路正常；这次拖到了 `x = -929`，日志里立刻变成"无保存位置"。
  **编译通过、静态检查、字符串扫描，全都不可能发现它。**
- **修复**：改成跟哨兵值比。
  ```cpp
  if (sx != -1 && sy != -1) {
  ```
- **本机为什么必现**：用户的两块屏是 `DISPLAY1`（主，X 从 0 起）和
  `DISPLAY26`（副，**X 从 -1463 起**）—— 副屏在主屏左侧，坐标必为负。
- **通用教训**：**哨兵值不要选在合法值域里面或者紧挨着它。**
  坐标这类"全整数域都合法"的量，本来就不该用数值当哨兵 ——
  更稳的做法是单独存一个 `cfg_panel_saved` 布尔量。
  这里保留 -1 哨兵是为了兼容已有配置，但判断必须写成 `!= -1`。

## D-024 LRCLIB 用真实数据探过底：搜索接口会张冠李戴，503 不等于 404

- **怎么发现的**：拿用户真实曲库去问 LRCLIB，而不是等写完再测。三次探测：

  | 探测 | 结果 |
  |---|---|
  | 精确查 `純白P / Best Wishes` | **404 TrackNotFound** —— 这首中文同人曲没有 |
  | 搜索 `Best Wishes` | **返回 Duane Betts 的同名歌**（完全不相干） |
  | 精确查 `塞壬唱片-MSR / Battleplan Obliteration` | **503 ServerOverloaded** |
  | 搜索 `Battleplan Obliteration` | `[]` 空 —— 用户这首 OST 也没有 |
  | 搜索 `周杰伦 晴天` | ✅ 命中，歌词完整，`duration: 270.0` |

- **结论一：覆盖面**。主流中文歌（周杰伦这类）LRCLIB 覆盖**很好**；
  同人曲 / 游戏 OST（純白P、塞壬唱片-MSR）**基本没有**。
  这个功能对用户的部分曲库有用，不是万能 —— 别过度承诺。

- **结论二（更重要）：`/api/search` 会返回错误的歌。**
  直接取第一条结果 = 在 A 歌上显示 B 歌的歌词，
  正是本项目反复强调的**「找错歌词比找不到更糟」**。
  → 所以 `OnlineLyricResult` 必须带回 `matchedArtist` / `matchedTrack` /
  `matchedDuration` / `fromSearch`，由调用方核对后才敢用。
  **时长是最强的判据**：LRCLIB 返回的 `duration` 与本地 `playback_get_length()`
  差超过几秒就该丢掉。

- **结论三：503 必须和 404 分开。**
  - `404` = 确实没有 → 写 miss 标记，7 天过期
  - `503` / 其他 5xx / 超时 = 服务端问题 → **绝不能写 miss 标记**，
    否则一次服务端抖动就把这首歌永久记成"没有"，而且用户永远不会知道为什么。
  - 这两条路径在**缓存层**就要分开，不能等上层判断。

- **教训**：与其等代码写完再拿真实数据试，不如**先探接口**。
  这三次 curl 花了两分钟，改掉的是三个会写进代码的假设。

### 验证记录（2026-09-23，真机）

用**静音 WAV 夹具**（时长对齐 LRCLIB 返回值）把每条路径都跑了一遍：

| 场景 | 夹具 | 结果 |
|---|---|---|
| 精确命中 + 缓存写入 | `周杰伦 - 晴天.wav` 270s | ✅ `/api/get` 404 → 搜索命中 → 缓存 `.lrc`+`.meta` |
| 缓存命中 + `.meta` 往返 | 同上，再播一次 | ✅ `缓存命中（…，模糊搜索来的，调用方需核对）` |
| **503 重试** | 同上 | ✅ 真实过载两次：`600ms 后重试` → `1500ms 后重试` → `最终 200` |
| **同名的别人的歌** | `Best Wishes.wav` 240s | ✅ 返回 Ultrasound 的同名歌 328s；**曲名放行、时长 88 秒之差拦截** |
| 确实没有 | `純白P - Best Wishes.wav` 240s | ✅ `已写 7 天有效的标记` → `.miss` 15 字节 |

- **时长闸门是真管用的**：`Best Wishes` 这一例里曲名完全一致，
  全靠时长把 Ultrasound 那首挡在外面。**没有它就会张冠李戴。**
- **夹具做静音的**：这样能在不发出任何声音的前提下跑完整链路 ——
  半夜测、用户正在用电脑时测，都不打扰人。见 D-027。

- **顺带测掉了「只有纯文本歌词」这个担忧**：原本打算支持
  `plainLyrics`（无时间轴），那要改渲染层的时间轴模型，工作量不小。
  先抽样量了一下：**8 首（中/英/日、主流）全部带 `syncedLyrics`，0 首只有纯文本。**

  → **这个缺口在实践中不存在，不必为它改渲染层。**
  这是个**有价值的否定结论**：花两次 curl 的时间，省掉一整块工作。
  以后遇到"要不要支持 X"的犹豫，先量一下 X 到底占多少，再决定。

## D-023 `windef.h` 的 `min`/`max` 宏会撕开 `std::min` / `std::max`

- **症状**：`error C2589: "(":"::"右边的非法标记`，指向 `std::min(a, b)` 那一行。
  报错信息完全不提宏，第一眼看像是语法错误。
- **原因**：`windef.h` 把 `min` / `max` 定义成了函数式宏，
  `std::min(a,b)` 被预处理器展开成 `std::(((a)<(b))?(a):(b))`。
  而 `windows.h` 是由 `helpers/foobar2000+atl.h` 间接带进来的，躲不开。
- **本工程已经踩过两次**：
  * `lyrics_view.cpp` —— 当时的处置是**整个文件不用 std::min/max，全部手写比较**；
  * `lyric_search.cpp:530` —— `(std::min)(ba.size(), bb.size())`。
- **两种写法都可以，但都要配注释**：
  ```cpp
  // 加括号挡住宏展开。别删这对括号 —— 删了就编不过。
  (std::min)(a, b);

  // 或者手写
  const int m = (a < b) ? a : b;
  ```
  括号写法保留了 `std::min` 的语义（尤其对自定义比较器），**优先用它**。
- **为什么不干脆加 `NOMINMAX`**：那要动全局预处理宏，而 SDK / WTL / libPPUI
  都不是按 `NOMINMAX` 写的，风险不对等 —— 为了一个一行的局部问题改全局开关，
  可能换来一堆别处编不过。**已评估并否决**，不要再提。
  真要试的话，单独一个改动单独验证，别和功能混在一起。

## D-020 CUI 面板走 common_callback（全局配色 + 公共字体），不做 per-panel 客户端

- **决定**：CUI 面板用 `cui::colours::helper`（无 client GUID）+ `cui::fonts::manager::get_font`，
  配 `common_callback` 通知路径。**暂不做** per-panel 的 `cui::colours::client` / `fonts::client`。
- **理由**：per-panel 路线要让用户在 CUI 偏好页里多两个客户端条目，我们还得维护一张**活面板表**
  来分发通知 —— 收益仅是"用户能单独给歌词面板配色"。等真有人提这个需求再说。
- **顺带一个意外收获**：`cui::colours::common_callback`（colours.h:102）与
  `cui::fonts::common_callback`（fonts.h:60）**都不继承 `service_base`**，是两个纯接口。
  所以把它们挂在面板类上**不会产生第二个 `service_base` 分支** —— 原本担心的菱形继承问题自然消失，
  主题回调可以直接落在面板实例上（多开几个面板各收各的通知，不需要活面板注册表）。
